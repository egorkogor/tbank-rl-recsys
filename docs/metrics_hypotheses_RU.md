# Дерево метрик, гипотезы и правило выбора

> **Поправка владельца, 24.10, 18:50–19:10 (до полной оценки и OOT).** Главная метрика — **сбалансированные минуты** B = T · K(s).
> - T — все минуты недели; s — доля новой музыки, то есть треков, которых пользователь раньше не слушал (артист неважен: у старых артистов может не быть новинок).
> - BC(s) = √(s · s\*) + √((1 − s)(1 − s\*)), где s\* = 0,278 — доля новой музыки в обучающем периоде.
> - K = BC² при s ≤ s\*; K = 1 − 0,25 · (1 − BC²) при s > s\*: избыток нового штрафуется в 4 раза мягче, чем недобор.
> - Штраф: 0% нового — −27,8%; 10% — −5,4%; 50/50 — −1,3%; 100% нового — −18%.
> - B ≤ T, равенство при s = s\*; B читается в минутах и растёт без потолка.
> - На неделе val: B = 377 при T = 395 (средний K = 0,93); для +2% нужно 34 тыс. пользователей на группу (CUPED, ρ = 0,70).
> - Голые минуты и открытие артистов остаются вторичными метриками. Цель правила выбора (раздел 3) — прирост B у судей.

Зафиксировано 24.10.2026, около 18:20: **до** полной оценки на val (все пользователь-дни, бутстрэп, судьи, разложение) и **до** OOT. Главную метрику и метрику возвратов выбрал владелец.

## 1. Дерево метрик

## 2. Гипотезы

Правила решения (как в задании 1, пороги зафиксированы):
- «лучше» — нижняя граница 95% CI для Δ > 0;
- «хуже» — верхняя граница < 0;
- «сопоставимо» — CI содержит 0 и |Δ| < 2% от SFT по релевантности или < 0,005 по вероятностям судей;
- иначе — «не определено».

| № | Гипотеза | Механизм | Как проверяем | Статус до проверки |
|---|---|---|---|---|
| H1 | При β = 0,5 у любой награды из RM NDCG@10 «сопоставимо» с SFT; при β = 0,02 — «хуже» для lp, ratio, fair, disc | KL держит политику у π_ref | `compare.py`, бутстрэп | видели |
| H2 | Балл судей растёт меньше обучающего балла; разрыв растёт с KL; у судей на снимке начала дня (m4–m6) он больше, чем у m1–m3 | политика эксплуатирует ошибки m0; m1–m3 — почти копии m0 | `compare.py`: r_train − r_judge, r_judge_snap | вслепую |
| H3 | lp и ratio укорачивают треки, minutes удлиняет, fair перекорректирует в длинные | доля дослушивания падает с длиной, минуты растут | средняя длина top-10 | видели для lp, ratio, fair; minutes — вслепую |
| H4 | При β ≤ 0,1 больше половины прироста балла судей — «состав» (сдвиг к коротким / популярным / повторным), а не «внутри групп» | дешевле сменить тип трека, чем найти лучший трек того же типа | `decompose.py` | вслепую |
| H5 | Коллапс (самый частый трек > 15% пользователь-дней) только при β = 0,02 у placebo и disc; при β ≥ 0,1 — нет | разброс награды между треками против силы KL | поведенческие метрики | видели |
| H6 | При T = 1 RL не обгоняет π\*_β той же награды и β по обучающей цели; недобор β · KL(π_RL ‖ π\*_β) > 0 и растёт при меньшем β | конечные шаги, сэмплирование 16 из 100 тыс. | π\*_β против RL, KL на топ-1000 | вслепую |
| H7 | `cont` не сдвигает политику (KL < 0,05); сессионные минуты при T = 5 дают больше минут сессии у судей, чем минуты за трек при T = 1 и том же β | P(cont) почти константа; сессионная награда учитывает выживание сессии | сетка, `compare.py` | `cont` — видели; T = 5 — вслепую |
| H8 | В открытом цикле hit@10 падает с номером шага, разброс ансамбля растёт; в режиме «исход подставляет RM» r_train выше, чем в режиме с реальными событиями дня | контекст уходит от реальной истории; RM сама себе рисует «дослушанные» треки | `eval_multistep.py` | вслепую |
| H9 | Бустинг-судья из задания 1 ранжирует модели так же, как судьи RM, только для β ≥ 0,1; при β = 0,02 RM-судьи переоценивают RL | разные семейства ошибаются по-разному вне носителя | `booster_judge.py` | вслепую |
| H10 | Рекомендуемая точка RL дает офлайн-прирост минут сессии < 5%, то есть на 9 тыс. пользователей его не проверить; нужен A/B на ≥ 5,5 тыс. пользователей на группу | — | правило ниже + `ab_power.json` | вслепую |

## 3. Правило выбора рекомендуемой точки (до OOT)

**Кандидаты:** все контрольные точки RL и π\*_β на val.

**Цель:** максимум прироста ожидаемых минут сессии top-10 у судей. Используются судьи m4–m6, если обучены, иначе m1–m3.

**Ограничения против SFT:**
1. NDCG@10 — вердикт не «хуже» и Δ ≥ −2% от SFT;
2. Recall@100 на новых для пользователя треках — Δ ≥ −10% от SFT (открытие не проседает);
3. P(skip) судей в top-10 — не выше SFT больше чем на 0,005;
4. доля самого частого трека — не больше 2 × SFT.

Кандидаты, нарушившие хоть одно ограничение, отбрасываются.

**OOT:** выбранная точка, SFT, лучший π\* и бейзлайны — один прогон после `freeze.json`.

**Если по главной метрике ни одна точка не прошла,** рекомендуем SFT и честно пишем, что RL против этой RM офлайн не даёт безопасного прироста минут.
