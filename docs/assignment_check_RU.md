## Ограничения, которые влияют на вывод

- Оптимизируется отклик RM. Его рост не равен росту удовлетворённости, реальных минут или удержания.
- Для T = 5 в регуляризации есть локальный KL в посещённых префиксах, но отсутствует градиент изменения распределения будущих состояний для KL. Это ограничение реализации, а не проверка точного оптимума по траектории.
- RM-судьи относятся к тому же семейству и используют общую исходную модель. Внешний бустинг — дополнительная проверка, а не независимая оценка удовлетворённости.
- R1 и R2 измеряют пересечение выдачи с логом старой системы. Это не контрфактическое время прослушивания нового списка.
- Проверено много настроек на val, без поправки на множественные сравнения; RL — один сид на конфигурацию.
- Исходное OOT осталось проверкой первоначального выбора. Штраф за длину и связанные выводы относятся к диагностике после вскрытия; второй прогон OOT не является независимым тестом.

## Открытые вопросы

1. Для полного воспроизведения нужен доступ к подготовке `events.parquet` и `items.parquet` из задания №1. В README приведён контракт, но ссылка на опубликованный репозиторий задания №1 пока не задана.
2. Для R1 нужно проверить чувствительность к неполному горизонту лайка на конце лога. Это можно сделать по сохранённым выдачам, с пометкой о диагностике после OOT. Такой пересчёт пока не выполнен.
3. Если продолжать многошаговый RL, нужно исправить учёт KL по траектории и обучить RM на подходящих сгенерированных префиксах. Проверять это следует в новом протоколе, без повторного подбора на текущем OOT.
4. Перед A/B нужны дисперсии и интервалы наблюдения самого сервиса. Расчёт по Yambda — ориентир; офлайн-прирост B не является прогнозом онлайн-эффекта.

В этой сетке RL не обогнал более простое переранжирование по RM. Диагностика показала, что рост награды может сопровождаться падением NDCG, а прирост модельных минут зависит от длины треков.
