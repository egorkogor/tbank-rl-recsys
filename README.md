# RL-дообучение последовательного рекомендателя против модели вознаграждения (Yambda-50M)

Тестовое задание Т-Банка № 2. GPT-2 предсказывает следующий трек; модель вознаграждения (RM) предсказывает отклик; политику дообучаем RL против RM. Главный вопрос — становятся ли рекомендации от этого лучше по-настоящему или модель учится угождать RM.

> Числа val — полная оценка: 31 459 пользователь-дней, парный бутстрэп по пользователям, 7 членов RM. Числа OOT получены одним прогоном после заморозки (`artifacts/freeze.json`); они в разделе 8. Исключение — одна модель из 8.3: её выбрали после вскрытия OOT и прогнали на OOT вторым, помеченным прогоном. Журнал решений — `docs/decisions_RU.md`.

## 0. Коротко

1. **Повторы определяют метрику.** Голая GPT-2 в 5 раз хуже правила «повтори любимое»: NDCG@10 0,035 против 0,192. Канал повторов в духе RepeatNet поднимает её до 0,173. Простое усиление этого канала даёт 0,202 — лучший результат по релевантности без всякого RL.
2. **RL максимизирует награду и при слабом KL-поводке взламывает её.**
   - Для наград-вероятностей: короткие треки, одинаковая выдача, NDCG −19…−71%.
   - Для наград в минутах: 10–22-минутные треки всем пользователям, NDCG ≈ 0.
   - Все судьи семейства RM и внешний судья (бустинг из задания 1) ставят взломанной выдаче более высокий балл. Значит, обманута сама цель, а не только модель: короткие треки действительно дослушивают чаще.
   - Ловят взлом только релевантность и концентрация выдачи, поэтому в правиле выбора они стоят ограничениями.
3. **При одношаговой генерации RL не нужен.** У задачи «награда − β · KL» есть закрытая форма π\* ∝ π_ref · exp(r / β) — переранжирование кандидатов исходной модели по RM. По зафиксированному заранее правилу она лучше любого RL-прогона.
   - Выбранная точка — π\* для награды «минуты» при β = 2: сбалансированные минуты +25% при NDCG +0,1%. При пересчёте с нейтральной длиной прирост этой точки исчезает (п. 6).
   - Лучший RL-прогон даёт +8%.
   - π\* для «дослушает» поднимает и NDCG (+3,2%), и вероятность дослушать. RL с той же наградой их роняет.
4. **Формулы из литературы против перекоса по длительности (WTG, линейная полезность) в RL сами становятся взломом.** Они создавались для обучения предсказателя, а не как награда под давлением оптимизатора.
5. **Долгосрочные цели на уровне трека** («продолжит сессию», «откроет артиста») либо почти не двигают политику, либо схлопываются. Офлайн-оценка не доказывает онлайн-эффект. Для +5% главной метрики расчёт даёт около 5,4 тыс. пользователей на группу онлайн (`artifacts/runs/ab_power.json`).
6. **Прирост B выбранной точки исчезает при нейтральной длине** (диагностика после вскрытия OOT, разделы 8.1–8.3).
   - Пересчитаем тот же B, подставив каждому треку привычную пользователю длину. На OOT вместо +3,99 получается −0,23 [−0,25; −0,21] (`artifacts/runs/eval/oot/diag/diag.json`). Это результат для выбранной точки; у других наград остаток отличается.
   - Штраф за отход от привычной длины убирает перекос. На OOT B +10,7%, выполнены все шесть ограничений, пропуски и дослушивание лучше SFT. Но и здесь без длины прирост −0,01 [−0,02; +0,01]: положительный остаток не подтверждён (`artifacts/runs/eval/oot/diag/diag.json`).
   - Среди моделей этой диагностики по логу лучшая — усиленный канал повторов, без RM: на OOT NDCG по лайкнутым за день трекам +22%, доля реальных минут дня в топ-10 +19% (`artifacts/runs/eval/oot/diag/diag.json`).
   - Модельный судья лайков обманут коллапсами так же, как судьи дослушивания. Взлом ловят только метрики по логу.

## 1. Постановка

- **Продуктовая рамка** — «Моя волна»: сервис сам ставит следующий трек.
- **Политика** π_θ(a | s) — GPT-2 по истории прослушиваний. Токены — 100 тыс. самых частых треков; к ним добавляются эмбеддинги исхода, органики и интервала.
- **RM** r(s, a) — по истории и треку-кандидату предсказывает отклик.
- **RL** максимизирует E[Σ_t r(s ⊕ a_<t, a_t)] − β · Σ_t KL(π_θ ‖ π_ref):
  - T = 1 — следующий трек;
  - T = 5 — последовательность; сгенерированный трек дописывается в контекст с исходом «неизвестно».

**Что на самом деле имитирует next item.** Почти половина прослушиваний органические, остальные выбрал прод. Поэтому SFT клонирует смесь «пользователь + логирующая политика». Релевантность меряем не по следующему событию, а по множеству треков, которые пользователь дослушал в день оценки.

## 3. Разбиение и защита от утечек

| Часть | Дни | Зачем |
|---|---|---|
| Обучение | 0–286 | SFT, RM, словарь, статистики |

- **Контекст** пользователь-дня — только события до начала дня, как в Global Temporal Split статьи Yambda.
- **Метки RM с горизонтом** (лайк за 24 ч, продолжение за 30 минут, «открытие» за 7 дней) берутся только у событий, чей горизонт закрыт до отсечки.
- **Тесты** (`tests/test_no_leakage.py`, 6 из 6):
  - контекст строго до дня;
  - выход политики не меняется при перемешивании будущих событий;
  - словарь только по дням обучения;
  - горизонт меток закрыт;
  - признаки RM совпадают при обучении и применении;
  - цели дня — ровно Listen+ этого дня.
- **OOT** запускается только при наличии `freeze.json` (коммит, пороги, хэши всех чекпойнтов, состав) и не перезаписывается.

## 4. Модели

**SFT.** GPT-2, 4 слоя, d = 256, окно 256.
- Вход позиции — эмбеддинги трека, исхода (пропуск / частично / Listen+ / неизвестно), органики и интервала; выход связан с эмбеддингами треков.
- Кросс-энтропия по всему словарю кусками с пересчётом в обратном проходе.
- **Канал повторов:** логит(v) += w₀ · log1p(число v в контексте) + w₁ · log1p(число v в последних 32 событиях). Веса учатся, итог (2,3; 0,7).

**RM.** Бэкбон GPT-2 (инициализирован весами SFT) + MLP([h, e, h ⊙ e, side]).
- 6 голов: доля дослушивания, Listen+, пропуск, лайк, продолжение сессии, «открытие» артиста.
- Признаки side: длина и популярность трека, сколько раз пользователь слушал трек и артиста, сглаженные доли Listen+ и пропусков пары «пользователь × трек» (сильнейшие признаки в задании 1), доля Listen+ артиста.

**Ансамбль из 7 членов, на разных 80% пользователей:**
- m0 учит политику;
- судьи m1–m3 обучены так же, как m0 — на окнах с исходами этого же дня;
- судьи m4–m6 обучены на снимке начала дня, то есть так, как RM применяется в RL.

**RL.** REINFORCE с leave-one-out бейзлайном (RLOO), G = 16 сэмплов на состояние, точный KL по всему словарю, строго on-policy, 400 шагов.
- Без деления преимущества на std, поэтому стационарная точка при T = 1 — ровно π\*_β, и β сравним с закрытой формой.
- При T = 5 — накопление градиента по целым состояниям.

|---|---|---|

| `fair` | Listen+ минус средняя Listen+ для такой длины | наша поправка |
| `cont` | P(сессия продолжится) | долгосрочная цель |
| `disc` | Listen+ + 2 · P(открытие нового артиста) | долгосрочная цель |

| `mlp` | Z(минуты) + Z(Listen+) | идея владельца: бонус за дослушивание |

| `add` | Z(минуты) + 0,25 · Z(лайк) − 0,25 · Z(пропуск) | по схеме FeedRec, KDD'19 |

## 6. Дерево метрик и правило выбора

Зафиксированы до полной оценки и OOT: `docs/metrics_hypotheses_RU.md`.

**Главная метрика (выбор владельца)** — сбалансированные минуты на пользователя в неделю: **B = T · K(s)**.
- T — минуты; s — доля новой музыки (треки, которых человек не слышал, артист неважен).
- K = BC² при s ≤ s\* и 1 − 0,25 · (1 − BC²) при s > s\*, где BC = √(s · s\*) + √((1 − s)(1 − s\*)) и s\* = 0,278 — доля новой музыки в обучении.
- Свойства: B ≤ T, равенство ровно при целевой доле; метрика читается в минутах и растёт без потолка; избыток нового штрафуется вчетверо мягче недобора. Штраф: без нового −27,8%, 50/50 −1,3%.
- Офлайн B считаем по неделе пользователя до дня, к которой добавлен топ-10 как сессия (минуты с поправкой на выживание сессии).

**Вторичные метрики:** минуты, сессии в неделю, открытие артистов.

**Правило выбора:** максимум прироста B у судей m4–m6 при пяти ограничениях против SFT:
1. NDCG@10 не «хуже» и Δ ≥ −2%;
2. Recall@100 на новых треках Δ ≥ −10%;
3. P(пропуск) не выше SFT больше чем на 0,005;
4. доля самого частого трека ≤ 2 × SFT;
5. P(Listen+) не ниже SFT больше чем на 0,005.

**Что видно:**
- **Награду RL поднимает, а точность при слабом поводке падает при любой награде.** Короткие треки — у наград-вероятностей (lp, ratio, mix), длинные — у наград в минутах (minutes, wtg, add, mlp).
- **Взлом не виден самим RM.** При β = 0 у «дослушает» все судьи ставят выдаче более высокую P(Listen+) (0,705 против 0,654), хотя NDCG упал на 71%. Это семейное слепое пятно RM: внешний судья другой архитектуры — в разделе 7.6.
- **Сила сдвига определяется разбросом награды между треками, а не её смыслом.**
  - Плацебо при β = 0,1 уходит дальше настоящих наград, его KL втрое выше.
  - Награды в минутах при β = 0,5 схлопываются, а вероятности при том же β почти не двигаются.
- **Слабый поводок вредит даже собственной цели.** У «минут» при β = 0,1 и 0,02 итоговые минуты ниже, чем при β = 0,5: оптимизация застревает в вырожденных решениях из 24–33 треков на всех.
- **Долгосрочные награды на уровне трека.** `cont` почти константа (P ≈ 0,94) и не двигает политику. `disc` при слабом поводке схлопывает выдачу в «открывающие» треки для всех.

![Компромисс награды и релевантности: RL против π*](docs/figures/tradeoff.png)

**Почему так:**
- π\* переранжирует сильного кандидата (топ-1000 SFT) знанием RM об истории пары «пользователь × трек». Поэтому для «дослушает» растут и точность, и награда.
- RL делает то же градиентами по 16 сэмплам из 100 тыс. действий за 400 шагов и не доходит до оптимума. Недобор β · KL(π_RL ‖ π\*) — в разделе 7.5.
- При одинаковом β RL достигает 80–90% прироста π\* для «минут», а для «дослушает» уходит в противоположную сторону по точности.

### 7.5. Выбор точки, разложение прироста и недобор RL

  - самый частый трек 3,0% (у SFT 3,5%);
  - уход от профиля длины 0,093, треки 217 с.

  Все шесть ограничений выполнены по сохранённым оценкам (`artifacts/runs/eval/oot/sft.json`, `artifacts/runs/eval/oot/pistarlen__minutes__2__2.json`; вердикт NDCG — `artifacts/runs/eval/oot/compare_balanced.json`).
- **Положительный остаток без длины не подтверждён:** при нейтральной длине −0,01 [−0,02; +0,01]. ДИ допускает небольшой эффект обоих знаков. Штраф ограничил удлинение; улучшение B сверх него не доказано. Треки на 9% длиннее, но ближе к привычному профилю пользователя, чем у SFT.
- **Вывод для A/B.** У выбранной версии положительный прирост B без удлинения не подтверждён: внутри пользователя она различает треки слабо (GAUC 0,58, раздел 7.2). Гипотеза для A/B — «немного более длинные треки в пределах привычного профиля увеличивают минуты без снижения дослушивания». Офлайн +10,7% модельного B не задаёт размер онлайн-эффекта. Гипотеза «RM нашла треки, которые нравятся больше» не подтверждается. Защитная метрика A/B — уход от профиля длины.

## 9. Генерация на 5 шагов

`eval_multistep.py`, 3 610 пользователь-дней val, жадный выбор лучшего трека на каждом шаге. Три режима контекста:
- **открытый цикл** — сгенерированный трек дописывается с исходом «неизвестно»;
- **исход подставляет RM** — дописывается с исходом, который предсказала RM;
- **реальные события дня** — оракул: в контексте реальные первые k − 1 прослушиваний дня.

| SFT | шаг 1 | 2 | 3 | 5 |
|---|---|---|---|---|
| NDCG@10, открытый цикл | 0,184 | 0,178 | 0,176 | 0,175 |
| NDCG@10, реальные события | 0,184 | 0,199 | 0,210 | **0,229** |
| P(Listen+) по RM, открытый цикл | 0,651 | 0,752 | 0,771 | **0,800** |
| P(Listen+) по RM, исход подставляет RM | 0,651 | 0,727 | 0,731 | 0,745 |
| P(Listen+) по RM, реальные события | 0,651 | 0,667 | 0,649 | 0,654 |
| Трек повторяет предыдущий сгенерированный (открытый цикл) | — | 92% | **100%** | 100% |
| Разброс ансамбля RM, открытый цикл | 0,020 | 0,016 | 0,016 | 0,016 |

- **Самоподкрепляющийся цикл.** Сгенерированный трек попадает в историю как прослушанный, канал повторов считает его повтором, и модель ставит его снова. С третьего шага цепочка состоит из одного трека.
- **RM принимает цикл за успех.** Её балл растёт с 0,65 до 0,80, судьи согласны, а NDCG падает. На реальном контексте балл стоит на месте, а NDCG растёт: реальные события дня — самая ценная информация. Разрыв к пятому шагу — 24%.
- **Разброс ансамбля падает, а не растёт.** Все члены одинаково уверенно ошибаются на выдуманном контексте, поэтому как сигнал неуверенности он здесь не работает. Гипотеза H8 подтвердилась частично: точность падает, балл RM на выдуманном контексте завышен, а неуверенность ансамбля не растёт.
- **RL при T = 5** (lp, β = 0,1) этот цикл не исправил: картина та же, что у RL при T = 1 и у SFT.
- **Вывод для продукта:** сгенерированная рекомендация — не прослушивание. При многошаговой генерации её нельзя засчитывать в повторы и в счётчики, а повторы внутри цепочки нужно запрещать. Режим с таким запретом (`open_ban`) — ниже.

**Запрет повторять сгенерированное внутри цепочки** (`open_ban`, те же 3 610 пользователь-дней):

| | шаг 1 | 2 | 3 | 5 |
|---|---|---|---|---|
| NDCG@10, SFT, запрет повторов | 0,184 | 0,156 | 0,140 | 0,117 |
| P(Listen+) по RM, SFT, запрет повторов | 0,651 | 0,751 | 0,768 | 0,795 |
| Тот же артист, что на прошлом шаге | — | 8% | 8% | 7% |
| NDCG@10 на шаге 5: RL lp 0,1 при T = 1 / T = 5; RL balanced 5 | | | | 0,113 / 0,110 / 0,118 |

- **Цепочка становится разнообразной** (повтор артиста 7–8% вместо 100%), но NDCG падает быстрее. Модель расходует лучших кандидатов — любимые треки пользователя, — а запрещённые уже не попадают в топ-10. Часть падения механическая.
- **Устойчивый вывод не зависит от режима:** на выдуманном контексте балл RM растёт с каждым шагом (0,65 → 0,80), хотя реальная точность падает. RM систематически завышает награду для сгенерированных продолжений, а разброс ансамбля этого не показывает.
- **Следствие для многошаговой RL-цели.** Награда на шагах t > 1 смещена вверх, поэтому оптимизация последовательности против такой RM вознаграждает «уверенность в выдуманной сессии». Нужна RM, обученная на сгенерированных или частично наблюдаемых контекстах, либо онлайн-обратная связь.
- **RL при T = 5 ведёт себя как RL при T = 1:** обучение на последовательности не изменило ни цикл, ни завышение.

## 10. Долгосрочные цели

- **Что проверяется офлайн:**
  - предсказательная сила сигналов: AUC продолжения 0,61, открытия 0,70;
  - растут ли они у судей после RL;
  - не уходит ли политика в повторы.
- **Что не проверяется офлайн:**
  - причинный эффект на возвраты и удержание;
  - петли обратной связи;
  - привыкание;
  - удовлетворённость.
- **Размеры A/B** по дисперсии Yambda (CUPED по прошлой неделе, α = 0,05, мощность 80%):
  - сбалансированные минуты B: +2% → 34 тыс., +5% → 5,4 тыс. пользователей на группу;
  - сессии: +2% → 12 тыс.;
  - освоенные новые артисты: +2% → 462 тыс. — поэтому открытие остаётся защитной метрикой, а не целью.
- **Как это делает Яндекс публично** (`docs/yandex_practice_RU.md`):
  - модель учится на порядковом отклике «пропуск < дослушал < лайк» попарно на соседних показах (ARGUS);
  - онлайн смотрят время прослушивания и активных пользователей (Sona: +6,3% и +4,5%), открытия и дизлайки — как защитные метрики;
  - пожелания вроде «реже длинное» советуют решать переранжированием, а не таргетом (хендбук ШАД).

## 11. Ограничения

- **Судьи m1–m3 почти копии m0.** Судьи m4–m6 независимее, но это то же семейство RM: при взломе все они ошибаются в одну сторону. Внешний судья — бустинг.
- **RM учится только на показах логирующей политики.** Вне её носителя она экстраполирует; пропенсити нет, IPS невозможен.
- **OOT без переобучения:** разрыв 8–14 дней против 1–7 на val.
- **Словарь 100 тыс.:** часть целей вне словаря. В сохранённых сводках потолок Recall ≈ 0,85 не подтверждён, поэтому численную оценку здесь не используем.
- **Награды в минутах требуют своего масштаба β.** Сравнение идёт по достигнутому KL, а не по одинаковому β.
- **RL — один сид на конфигурацию** (код `src/rlrec/config.py`); в итоговых оценках используются контрольные точки шага 400 (`artifacts/runs/eval/val/selection.json`).
- **Все модельные судьи предсказывают отклик, а не удовлетворённость.** Это RM m1–m6 (включая голову лайка) и бустинг. Взлом самой цели они не ловят. Его видят только метрики по логу: релевантность, NDCG по лайкнутым, реальные минуты дня (8.2) — и концентрация выдачи.
- **Выбранная правилом точка удлиняет треки на 27%; при нейтральной длине положительный прирост B исчезает** (8.1, `artifacts/runs/eval/oot/diag/diag.json`). Метрики «длина против привычной пользователю» в замороженном правиле не было. Версию со штрафом выбрали после вскрытия OOT, поэтому её прогон на OOT — второй.
- **Оценка на 5 шагов вперёд** опирается на ту же RM, которая на выдуманном контексте завышает награду.
- **Правило выбора и гипотезы** зафиксированы до полной оценки, но после быстрых оценок RL на подвыборке — в `metrics_hypotheses_RU.md` это помечено.

## 12. Как воспроизвести

**Что лежит в репозитории, а что нет.** В Git входят код, документы, рисунки и JSON с итоговыми агрегатами: заморозки, оценки val/OOT, сравнения, диагностика и расчёт A/B. Числа можно сверить без загрузки данных. В `booster_judge_b0_summary.json` оставлены средние и ДИ; идентификаторы пользователь-дней и построчные оценки исключены. Данные Yambda, чекпойнты, последовательности, выдачи `.npz` и логи обучения в Git не входят.

Для полного воспроизведения сначала подготовьте `events.parquet` и `items.parquet` в репозитории задания 1 tbank-recsys-autofeatures (загрузка через `scripts/download_yambda.py`, подготовка через `tbrec.data.prepare` в том репозитории). Укажите эту папку через `TBANK_DATA`; `scripts/prepare.py` соберёт локальные последовательности. Чекпойнты и выдачи получаются командами ниже после обучения. Для внешнего судьи также нужны подготовленные данные и модель задания 1; путь задаётся через `TBANK_TASK1`. Команды описывают исторический конвейер; замороженные OOT-результаты не перезапускаются при проверке сдачи.

```bash
python -m uv sync                                  # Python 3.12, torch 2.12 cu126, transformers 5.9
# events.parquet / items.parquet из подготовки Yambda-50M (TBANK_DATA указывает на папку)
python scripts/prepare.py                          # последовательности, словарь, пользователь-дни, история пар
python -m pytest -p no:cacheprovider tests         # тесты утечек
bash scripts/run_sft.sh --epochs 2 --out sft_nocopy --stop-at 6000      # без канала повторов -> sft_nocopy_s6000.pt
bash scripts/run_sft.sh --epochs 1 --max-steps 2500 --init sft_nocopy_s6000.pt --copy --lr 5e-4 --out sft_copy
bash scripts/queue_after_sft.sh                    # RM m0-m3 и их оценка
bash scripts/queue_rl.sh; bash scripts/queue_rl2.sh; bash scripts/queue_rl4.sh   # сетка RL
bash scripts/queue_evals.sh                        # судьи m4-m6, полная оценка val
bash scripts/queue_analysis.sh                     # выбор, сравнения, разложение, 5 шагов, бустинг-судья
bash scripts/queue_oot.sh                          # заморозка и один прогон OOT
python scripts/eval_policy.py --stage val pistarlen:minutes:2:0.5 pistarlen:minutes:2:1 pistarlen:minutes:2:2 pistarlen:minutes:2:4
bash scripts/queue_post_oot.sh                     # после вскрытия: выбор с 6-м ограничением, диагностика, второй прогон OOT
```

Ресурсы: RTX 4060 8 ГБ, один GPU-процесс за раз, 3 потока CPU. SFT — около 1,5 часа, RM — 12 минут на член, прогон RL — 2–30 минут.
